## 4. 個別理由の理想との差分

全6候補について12項目ずつ、計72判定を`content_review.json`・`content_review.md`に保存。各判定に出力JSON pointer、入力ファイル、関連ID/得点や本文を添えた。Codexの暫定内容判断であり、独立の人手評価ではない。

### 失敗例A：対象の番号付き帯がscore-free部分に残る

- 採点者／答案／候補／段階：rater_7 / 1514:1 / 1514_1__K1 / Stage 1→2。
- 生成原文： “which aligns with the rubric descriptors for Overall score 3.”（`stage1/1514_1__K1/parsed.json#/score_free_analysis/decision_explanation`）。
- 入力根拠：対象Overall=3。正本Stage 1は対象の得点数字・番号付き帯をscore_free_analysisに含めないよう指定。
- 問題：対象の説明に得点3の帯を明示し、そのままreference_analysisとしてStage 2へ渡る。構造的にtargetの得点フィールドを消すだけでは防げない。
- 改善判定：対象分析に得点・帯・復元可能な数値関係を残さず、履歴得点は明示的に区別して保持する。
- 原因仮説：rubric_connectionを埋める際に、記述だけでなくbandの数値も再生成した。
- 次回指示案：上流のrubric_connectionを番号を伴わない基準記述に限定する例をWorkで検討する。今回は正本を変えない。
- プロンプト以外：構造上の分離検査に加えて意味上の漏洩レビューが必要。機械ルールは複数形“scores 2 and 3”を見逃しており、網羅性は保証しない。

1868:1/K1には “The rubric for a score of 3 in Cohesion, Vocabulary, and Phraseology aligns with this evaluation.” がある。入力の対象Vocabulary/Phraseologyは4であり、score-free分離違反に加えて基準と観測得点の関係も未解決。これを本人の全Trait=3という事実として扱わない。

### 失敗例B：本人の判断関係より一般的な特徴の反復が中心

- 採点者／答案／候補／段階：rater_7 / 4902:1 / 4902_1__K1 / Stage 1。
- 生成原文： “the rater tends to prioritize cohesion and syntax.”（`score_free_analysis/insufficient_evidence/0`）。
- 入力根拠：履歴8630:1はOverall=3、Syntax=2、Phraseology=1、1462:1はOverall=3、Syntax=3、Phraseology=3、8722:1はOverall=5。対象はOverall=3、Cohesion=2、Syntax=3。
- 問題：得点profileと本文特徴の併存だけでは、本人が他観点よりCohesion/Syntaxを優先したことは分からない。不足証拠欄がむしろ優先度を再断定している。
- 改善判定：具体的な比較箇所、評価上の関係、反例を示し、優先度が未同定なら仮説・判断不能として明示する。
- 原因仮説：得点を説明する必要から、一般的なルーブリック解釈を本人固有の重視傾向に置き換えた。
- 次回指示案：上流で「評価の関係」と「特徴」を対にし、反例によって何が支持できなくなるかを記述させる。重み推定は求めない。
- プロンプト以外：3履歴だけでは比較対象が不足する。本文の多様性と本人得点の組合せが必要で、プロンプト変更だけで優先度を同定できるとは限らない。

### 失敗例C：引用の原文保持が不完全

- 採点者／答案／候補／段階：rater_7 / 4902:1 / 4902_1__K2 / Stage 1、履歴8722:1引用。
- 生成原文冒頭： “Dear Principle, If our school were to change the cafeteria food” 。
- 入力根拠冒頭：`Dear Principle,\r\n\r\nIf our school were to change the cafeteria food`（ここでは原改行を可視化）。
- 問題：語の大筋は存在するが、改行を空白に変更し、厳密な原文一致を満たさない。8630:1の長い引用にも不一致がある。
- 改善判定：短い連続区間を原文のまま引用し、出典と照合できる。
- 原因仮説：モデルによる空白・改行の正規化と長文引用の再生成。
- 次回指示案：上流で短い原文区間の保持を具体例で示す。
- プロンプト以外：引用の機械照合は引き続き必要。今回の原文は修復せず、不一致と意味的妥当性を分けて記録する。

## 6. 実装上の問題とプロンプト上の問題の区別

実装側では、実入力の正本一致、本人得点の照合、history固定、対象得点フィールドの分離、原出力保持、厳密JSON解析、再開時の保存済み呼出しスキップを確認した。`invariant_checks.json`は実入力12件の検査通過を記録する。

既知の実装上の限界は、最初の実行をフォアグラウンドで起動して停止ログが残らなかったこと、漏洩ルールが単純な語形に依存すること、構造検査が厳密なJSON Schema全体の実装ではなく正本例の必須キー・型と一部制約の検査であること。Traits辞書の全項目保持も構造検査だけでは保証しない。今回、内容検査を追加の採否条件にしていない。

モデル出力側の問題はStage 2のコード枠、Stage 1の数値帯持込み、根拠と判断関係の弱さ、引用の変更。正本にはすでに禁止・要求が書かれているため、単に未指定だったとは言えない。現モデル・設定での指示遵守の限界を含む。プロンプトだけで解決できるとは保証しない。

## 7. 次回調整の優先順位（最大3件）

1. **上流Stage 1：score-free部分の数値帯持込みを防ぐ。** rubric_connectionに許される記述と禁じる数値ラベルを対比する案をWorkで作成し、同じ対象・履歴で検証する。得点削除による自動救済はしない。
2. **Stage 2：JSONのみの形式と汚染時の扱いを検証する。** code fenceの禁止は既存正本にもある。出力例の示し方等の限定改訂を検討する。形式制約の導入は別の実装条件として記録し、今回の結果に遡及適用しない。コード枠を除いて一致したことを今回の成功率に加えない。
3. **上流Stage 1：短い正確な引用と、本人の評価関係・反例・判断保留の接続を強める。** 特徴名の反復や推測した優先度を、出典で支えた比較に置き換える。履歴不足なら情報不足として扱う。

Stage 3を同時に改訂する案を既定にしない。採用0件で下流の内容問題を観測していないため、まず上流・形式の問題を解決し、統合の評価可能性を確保する。追加の自動調整ループは実施していない。
